从临时建表走向 Migration，并理解关系查询

前几课用原始 SQL 快速建表，适合学习；真实项目需要可重复、可追踪的 schema 变更。本课先理解 Migration 的职责，再认识 Entity 关系的查询入口。

1. Migration 解决什么问题

  • 每次 schema 变更都有版本和顺序。
  • 新环境可以从零执行，已有环境只执行尚未完成的 migration。
  • 部署时不依赖手工复制 SQL。

SeaORM CLI 可以生成 migration 工程；migration 的 up 创建或修改结构，down 撤销最近一次变更。

2. 用 Table 构造器描述变更

use sea_orm_migration::prelude::*;

manager
    .create_table(
        Table::create()
            .table(User::Table)
            .if_not_exists()
            .col(ColumnDef::new(User::Id).integer().not_null().auto_increment().primary_key())
            .col(ColumnDef::new(User::Email).string().not_null().unique_key())
            .to_owned(),
    )
    .await?;

迁移代码表达的是 schema 意图；数据库差异由 migration 框架和后端适配处理。生产环境要把 migration 与应用版本一起审查。

3. Entity 声明关系

#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {
    #[sea_orm(has_many = "super::order::Entity")]
    Order,
}

impl Related<super::order::Entity> for Entity {
    fn to() -> RelationDef {
        Relation::Order.def()
    }
}

一对多关系通常由父实体的 has_many 和子实体的外键配合。关系声明不会自动加载数据，查询时仍要明确使用 find_with_related 或关联查询。

4. 实际例子：用户和订单

假设电商系统新增订单表。Migration 负责建表，Entity 关系负责查询“某个用户的全部订单”。

Table::create()
    .table(Order::Table)
    .if_not_exists()
    .col(ColumnDef::new(Order::Id).integer().not_null().auto_increment().primary_key())
    .col(ColumnDef::new(Order::UserId).integer().not_null())
    .col(ColumnDef::new(Order::Amount).decimal().not_null())
    .foreign_key(
        ForeignKey::create()
            .from(Order::Table, Order::UserId)
            .to(User::Table, User::Id),
    )
    .to_owned();

迁移成功后，父实体可以显式加载关联记录：

let (users, orders) = user::Entity::find()
    .find_with_related(order::Entity)
    .all(&db)
    .await?;

for (user, user_orders) in users.into_iter().zip(orders) {
    println!("{} has {} orders", user.email, user_orders.len());
}

这里的查询结果是“一个用户和它对应的订单列表”。如果只需要单个用户，也可以先按主键过滤，再调用 find_with_related。关系查询不会自动发生，必须在查询代码中明确指定。

5. 回忆练习

  2. up 和 down 分别承担什么职责？
  3. 声明 has_many 后，如何主动加载关联记录？
