从临时建表走向 Migration，并理解关系查询

前几课用原始 SQL 快速建表，适合学习；真实项目需要可重复、可追踪的 schema 变更。本课先理解 Migration 的职责，再认识 Entity 关系的查询入口。

1. Migration 解决什么问题

  • 每次 schema 变更都有版本和顺序。
  • 新环境可以从零执行，已有环境只执行尚未完成的 migration。
  • 部署时不依赖手工复制 SQL。

SeaORM CLI 可以生成 migration 工程；migration 的 up 创建或修改结构，down 撤销最近一次变更。

2. 用 Table 构造器描述变更

use sea_orm_migration::prelude::*;

manager
    .create_table(
        Table::create()
            .table(User::Table)
            .if_not_exists()
            .col(ColumnDef::new(User::Id).integer().not_null().auto_increment().primary_key())
            .col(ColumnDef::new(User::Email).string().not_null().unique_key())
            .to_owned(),
    )
    .await?;

迁移代码表达的是 schema 意图；数据库差异由 migration 框架和后端适配处理。生产环境要把 migration 与应用版本一起审查。

3. Entity 声明关系

#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {
    #[sea_orm(has_many = "super::order::Entity")]
    Order,
}

impl Related<super::order::Entity> for Entity {
    fn to() -> RelationDef {
        Relation::Order.def()
    }
}

一对多关系通常由父实体的 has_many 和子实体的外键配合。关系声明不会自动加载数据，查询时仍要明确使用 find_with_related 或关联查询。

4. 回忆练习

  1. 为什么生产环境不应每次启动都执行建表 SQL？
  2. up 和 down 分别承担什么职责？
  3. 声明 has_many 后，如何主动加载关联记录？

提交答案后再继续：用一句话区分 migration 和 Entity，并写出“父实体查询子实体”时要调用的 SeaORM 方法名。
