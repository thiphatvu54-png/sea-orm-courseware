Lesson 0014 · SeaORM · 约 20 分钟

按需求选择关联查询 API

先判断两个问题：你需要完整 Model 还是少数列？关系是一对一还是一对多？答案决定 API，也决定最终 SQL 的形状。

1. find_with_related：完整 Model + 批量关联

let rows: Vec<(user::Model, Vec<post::Model>)> = user::Entity::find()
    .find_with_related(post::Entity)
    .all(db)
    .await?;

适合旧实体和完整父子 Model。它通常执行两条 SQL（以下为 PostgreSQL 风格的概念 SQL）：

SELECT "user".*
FROM "user";

SELECT "post".*
FROM "post"
WHERE "post"."user_id" IN (1, 2, 3, ...);

结果由 ORM 按外键分组为 (user::Model, Vec<post::Model>)。

2. 嵌套 PartialModel：一对一关系的精确列投影

#[derive(DerivePartialModel)]
#[sea_orm(entity = "user::Entity")]
struct UserList {
    pub id: i32,
    pub email: String,
    #[sea_orm(nested)]
    pub profile: Option<ProfileList>,
}

#[derive(DerivePartialModel)]
#[sea_orm(entity = "profile::Entity")]
struct ProfileList {
    #[sea_orm(from_col = "display_name")]
    pub name: String,
}

let rows: Vec<UserList> = user::Entity::find()
    .left_join(profile::Entity)
    .into_partial_model()
    .all(db)
    .await?;

对应的概念 SQL 是一条左连接，只选择 DTO 需要的列：

SELECT
    "user"."id" AS "id",
    "user"."email" AS "email",
    "profile"."display_name" AS "profile_name"
FROM "user"
LEFT JOIN "profile"
    ON "user"."id" = "profile"."user_id";

这里 PartialModel 负责“选哪些列”和“如何映射字段”；Option 表示没有 profile 时为 None。

3. Entity Loader：SeaORM 2.0 的加载策略

let users = user::Entity::load()
    .with(post::Entity)
    .all(db)
    .await?;

对一对多关系，典型 SQL 形状仍是两条批量查询：

SELECT "user".*
FROM "user";

SELECT "post".*
FROM "post"
WHERE "post"."user_id" IN (1, 2, 3, ...);

它返回嵌套的 ModelEx，并自动选择 join 或批量加载策略；需要 #[sea_orm::model] 或 #[sea_orm::compact_model] 实体格式。

练习：需求是“用户列表只返回 id、email，并带每个用户文章的 title”。你会优先选择哪个 API？如果必须保留完整旧实体，选择会怎样变化？
